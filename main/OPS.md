# Инструкция по эксплуатации protator

*Транзитный прокси-коллектор и ротатор. Написано человеком, для человеков,
которым доверили сервер и не выдали инструкцию.*

Вообще-то всё просто: protator днём и ночью гоняет открытые списки прокси,
проверяет их, запихивает живых в очередь, и через эту очередь крутит ваши
HTTPS/HTTP/SOCKS5-соединения. Ротация = каждый запрос теоретически может
уйти через другой адрес. Это система для тех, кто ценит приватность и
немного адреналина.

Три вещи, которые надо понять прямо сейчас:

1. **cert — это конфиг, а не «как-нибудь».**
2. **Очередь спасается в файл раз в минуту.** Если процесс убить жёстко,
   потеряешь максимум минуту работы. Это нормально, не переживай.
3. **Не удаляй файлы с расширением `.lst`, `.last`, `.txt` и папку `data/logs`**
   от скуки. Там данные. Они генерируются, но не «просто так».

---

## 1. Порты и кто на них живёт

| Порт | Роль | Кто ходит |
|------|------|-----------|
| `8888` | HTTP forward-прокси (туда же CONNECT/HTTPS-туннели) | браузер, curl, что угодно |
| `8443` | HTTPS (TLS) forward-прокси, самоподписанный серт | те, кто любит tls:// |
| `1080` | SOCKS5 | буфер обмена, Telegram-настроение |
| `9090` | **Админка** (только `127.0.0.1`, без пароля!): UI + `/health` + `/ready` + API, один порт на HTTP и HTTPS | ты, осторожно |

Если `9090` светится в интернет — ты сам подписал себе приговор. Инструкция
не поможет, поменяй `admin_listen` в конфиге. Подробности про вкладки и API —
раздел 4.6.

### Сертификаты: кому верить и зачем

Оба TLS-порта (`8443`, `9090`-по-https) отдают **самоподписанный серт,
который генерируется заново при каждом рестарте**. Выводы:

* **Админку открывай по `http://127.0.0.1:9090/`**, а не по `https://`.
  На loopback TLS не даёт ничего, а браузер будет ругаться на серт при
  каждом рестарте. Бонус за непослушание: страница обновляется раз в 15
  секунд, каждый рефреш — это пара оборванных handshake (`remote error:
  tls: bad certificate` в логах) и мёртвая страница. Шум теперь давится
  фильтром, но страница от этого не оживёт.
* **Скраперы цепляй на `http://127.0.0.1:8888`.** HTTPS-таргеты ходят через
  него CONNECT-туннелями, TLS при этом end-to-end до цели — серт прокси
  вообще не участвует. Порт `8443` нужен только клиентам, которые
  принципиально хотят `tls://`-схему прокси; им придётся выключить проверку
  серта (`curl -k`, `verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0`,
  `InsecureSkipVerify`) — или положить настоящий серт в
  `tls_cert_file`/`tls_key_file`.
* Ставить наш самоподписанный серт в trust store **бессмысленно**: после
  рестарта прилетит новый ключ, и всё сломается опять. Это by design,
  не баг.

## 2. Запуск

Скрипты, которые всё делают за тебя (исполняй из `main/`; на Windows
запрет на скрипты обходится так — да, это официально рекомендуемый
неофициальный приём):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
```

Что происходит: скрипт **убивает старый инстанс, если он есть** (это не баг,
это «рестарт»), потом стартует `main.exe` в фоне с `instance_err.log` на
перехвате ошибок. Проверка запуска:

```powershell
Get-Process -Name main | Select-Object Id,StartTime
Invoke-RestMethod http://127.0.0.1:9090/health
```

Ответ должен быть примерно такой (это базовая норма жизни):
```json
{
  "uptime_seconds": 820,
  "queue_live": 55230,
  "queue_hot": 4,
  "pool_candidates": 252122,
  "tls": false
}
```
Готовность: `/ready` отдаст `200` только когда в очереди есть живые прокси (`ok: true`), иначе `503` (`ok: false`). Админка одного порта (`9090`) отвечает и по HTTP, и по HTTPS (первая байтовая ловушка для TLS-handshake) — можно открывать `https://127.0.0.1:9090/` прямо в браузере без «ERR_SSL_RECORD_TOO_LONG».

### Проверка конфига без запуска

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Check
```

Выведет `config OK` и умрёт. Спасибо, что не стал запускать вслепую.

### Запуск вручную (для тестов/отладки)

```powershell
go run ./main -config config/config.toml
```

**Внимание:** бинарник читает файлы по относительным путям (`config/config.toml`,
`config/sites.txt`, `config/regexp.txt`, `config/checkers.toml`, `data/proxy.lst`,
`data/candidates.lst`, `data/logs/`). Запуск `go run ./main` из корня репозитория грустно споткнётся
о «файл не найден». Работай из корня репозитория.

## 3. Остановка

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\stop.ps1
```

Приятная ложь: скрипт называется «graceful stop», но на Windows процесс
убивается как есть. Настоящий graceful (дождаться завершения in-flight
запросов, `shutdown_timeout`, потом сохранить очередь) работает при
Ctrl+C и на Linux-сигнале SIGTERM. Вкладывать в него надежды на Windows не
надо, но и терять минуту очереди не страшно.

## 4. Конфиг: разбор по секциям

Файл: `config/config.toml`. Комментарии там уже подробные, вот выжимка самого
важного для оператора.

### `[server]`

| Ключ | Что делает | Если сломать |
|------|-----------|-------------|
| `listen` / `listen_https` | адреса HTTP/HTTPS прокси | сразу видно, порт занят |
| `max_proxies` | потолок живой очереди (2 млн) | ниже значения — очередь начнёт выбрасывать |
| `serve_retries` | сколько раз дёрнуть другой прокси при фейле | 0 = бумеранг на том же прокси |
| `serve_max_fails` | после скольких провалов выкинуть прокси | 0 = вечная вера в него |
| `pick_serve_window` / `pick_fresh_window` | окна «свежести» доказательства жизни для выбора апстрима (90s / 20m) | **важно:** `pick_fresh_window` должен быть **длиннее** `revalidate_interval` |
| `serve_total_timeout` | общий бюджет на запрос со всеми попытками (25s) | слишком мало = капризы |
| `serve_block_detect` | ловит «заглушки»/«капчи» и переспрашивает | выключишь — будешь видеть капчи в ответах браузера |
| `serve_connect_probe` | проверка, что CONNECT-туннель правда живой (3s) | 0 = старый тупой пасс-тру |
| `serve_response_probe` | то же для plain HTTP: первый байт ответа от дальнего конца (3s) | 0 = без надзора; чёрная дыра жжёт весь `response_header_timeout` |
| `shutdown_timeout` | бюджет graceful shutdown (10s) | 0 = мгновенный вылет с Ctrl+C |
| `admin_listen` | админка, `127.0.0.1:9090`, пусто = выключено. Один порт отвечает и по HTTP, и по HTTPS | «0.0.0.0:9090» = ты в курсе рисков? |
| `block_connect`, `waste_hosts`, `block_url_suffixes` | списки «это не трогаем» и «это превращаем в пустоту» | — |

### `[checker]`

Сердце валидации: 300 воркеров бегают по кандидатам, проверяют, что прокси
жив, не прозрачен, не выдаёт наш IP, а на тестовых URL отдаёт ожидаемый
контент. Долгие таймауты (до 230s на кандидата) — это норма, не удивляйся.

| Ключ | Что делает |
|------|-----------|
| `workers` | сколько прокси проверяются параллельно (600) |
| `require_stable_exit` | прокси, у которого IP прыгает между пробами, отбраковывается |
| `e2e_probe` | перед принятием гоняет настоящий GET через этот прокси |
| `leak_probe_urls` | проверка на слив `X-Forwarded-For` |
| `probe_order` | порядок протоколов для «голых» host:port кандидатов |

### `[collector]`

| Ключ | Что делает |
|------|-----------|
| `sites_file`, `regex_file` | откуда читаем списки и как выдираем ip:port |
| `cycle_sleep` | пауза между полными обходами сайтов (25m) |
| `fetch_retries` | сколько раз попытаться через запасные прокси |
| `use_browser` | Playwright-фоллбек. **По умолчанию выключен. Не включай** — надо ставить браузеры, а потом ты будешь объяснять, почему всё тормозит |
| `pool_retry_batch` / `pool_retry_interval` | кандидаты, что не прошли сейчас, перепроверяются позже (1000 раз в 3 минуты). 1000, не 20k: чекер — узкое место, 20k просто забивает канал |
| `max_candidates_per_site` | **cap на сайт за цикл (1000)**. Гигантские автосписки (100k+) не душат остальных; равномерная выборка. Остальное возвращается через pool_retry |
| `max_sites_per_cycle` | cap на число источников за цикл (60). Обход идёт в порядке приоритета, поэтому бюджет уходит на те, кто реально даёт; 60 держит цикл внутри одного интервала |
| `site_max_fails` / `site_cooldown` | после стольких подряд провалов источник уходит на паузу (3 / 30m по умолчанию) |

### `[storage]`

| Ключ | Что делает |
|------|-----------|
| `queue_file` | живая очередь (`proxy.lst`), спасается раз в минуту |
| `good_file` | аудит всех успешных (`good_proxies.last`) — скрытый пенсионный фонд |
| `candidates_file` | недожившие до валидации, переживают рестарт здесь |
| `revalidate_interval` | полная перепроверка очереди каждые 15 минут |
| `revalidate_fresh_servers` | «не трогай тех, кто недавно реально работал» (пассивная телеметрия) |
| `revalidate_max_per_pass` | **бюджет за проход (30000)** — очередь в 55k далеко не всегда успевает за 15 минут; лучше перепроверить 30k старейших, чем вечно догонять хвост |
| `max_bytes` | потолок размера файлов очереди (256MB) |

### `[logging]`

```toml
dir = "data/logs"
max_bytes = 33554432   # 32MB, потом ротация
keep = 5
```

Категории (всё дублируется в stderr):

| Файл | Что попадает |
|------|-------------|
| `logs/collector.log` | парсинг сайтов, капчи, фейлы загрузки |
| `logs/checker.log` | жизнь пайплайна валидации |
| `logs/serve.log` | реальные диалоги и невезучие прокси |
| `logs/system.log` | всё остальное: очередь, ревалидация, админка, шум |

Ротация: файл превысил 32MB → `foo.log` превращается в `foo.log.1`
(свежайший), старые отползают к `.log.2`…`.log.5`. **Ничего не удаляй —
ротация сама справится.**

Про шум: ошибки TLS-рукопожатий отловлены и выброшены, а поток
`WARN: Error dialing to host:port` от goproxy «сжимается» в одно сообщение
раз в 30 секунд. Поэтому в логах не кипит, хотя на самом деле там море.

## 4.5 Твои два лучших друга: `sites.txt` и `regexp.txt`

Это то, из чего **льзятся прокси**. Без них коллектор — как рыба-удильщик
без удочки: сидит, светится, но никого не ловит.

### `sites.txt` — откуда брать

Тот самый список источников. Коллектор читает его **каждый цикл**
(`[collector].cycle_sleep`, по умолчанию 25 минут) и тянет каждый URL.

Правила (они же написаны в шапке файла — это уже почти закон):

* **Один URL на строку.** Пустые строки — норм, `#` в начале строки —
  это комментарий, строка пропускается.
* **`github.com/.../blob/...` автоматически переписывается** в
  `raw.githubusercontent.com`. Так что можно смело кидать ссылку на страницу
  репозитория, не парься.
* **Порядок не важен, дубли дедуплицируются.**
* **Пагинация = несколько URL друг под другом.** Для API, где данные
  разбиты по страницам (`?page=1`, `?page=2`...), просто перечисляй
  страницы построчно. Смотри на `proxydb.net` в файле — там их целая
  пачка, и это норм.
* **Категории — только для тебя.** Заголовки-комментарии
  (`# ---- HTML proxy-list sites ----`) не влияют на работу: они для
  человека. Люби себя — разделяй.

Как проверить, что источник живой: открой URL в браузере. Если страница
открывается и там реально списки `ip:port` (или JSON/`txt` с ними) —
коллектор разберётся. Если там сплошная капча или «403 Forbidden» — убей
строку или оставь пережидать в коулдауне (см. `site_max_fails`).

Протокольная подсказка: файлы вроде `http.txt`/`socks5.txt` на GitHub-репо
помогают коллектору понять, какой протокол пробовать первым. Протокольные
«сырые» списки — самый ценный сорт корма: и формат простой, и протокол
подсказан честно.

Текущий `sites.txt` собран не «по памяти», а замером: каждый URL был скачан
настоящим экстрактором и оставлен только если он реально выдал кандидатов
(232 источника). Прежняя версия файла — 87 МБ мусора из 1.13M строк (среди них
`https://http://proxyapi.cf/y@n1@p1/google` и подобное) — лежит рядом под
именем `sites_legacy.txt` как история. В коллектор её не скармливай.

#### Как источник теряет доверие

`SiteRegistry` (`proxy/sitestats.go`) помнит по каждому источнику, сколько он
выдал кандидатов, сколько из них сейчас в живой очереди, сколько раз подряд
fetch падал. Порядок обхода — по этим данным:

1. источники, которые недавно давали живые прокси;
2. ещё не обойдённые (с детерминированным сдвигом по циклам, чтобы никто не
   голодал);
3. падающие — последними, и на `site_cooldown` после `site_max_fails` ошибок.
#### Почему «живых» прокси так мало и что с этим делать

`queue_live` в `/health` — это размер **очереди**, а не число работающих
прокси. После рестарта очередь засеивается из `proxy.lst` (десятки тысяч
записей), и в этом процессе их никто не проверял. Рабочий набор — это те,
кто прошёл проверку: смотри вкладку Live proxies со scope `checked` (или
`hot`), а не `queue_live`.

Именно поэтому выбор апстрима идёт по tiers: сначала кураторский хвост
(`hot`), потом всё, у кого есть доказательство жизни свежее
`pick_fresh_window`, и только потом — вся очередь. На типичной загрузке
(проверенных ~1–2%, остальное — не проверенные сиды) равномерный выбор
попадал бы в непроверенный прокси почти всегда.

**Главное правило:** `pick_fresh_window` (20m) должен быть длиннее
`revalidate_interval` (15m). Между двумя проходами ревалидации набор
«свежепроверенных» — это всё, во что picker может целиться; если окно
закроется раньше, он начнёт отдавать клиентам непроверенную массу очереди.
При старте приложение предупредит в лог, если окна конфликтуют.

Так что битый источник не нужно вычищать руками: он сам уходит в коулдаун.
Смотреть, кто чего стоит, удобнее на вкладке **Sources** в админке
(`GET /api/sources`): `yield_pct` — доля выданного, которая ещё жива, и это
тот самый показатель, по которому решается, кто нужен в списке.
| `max_sites_per_cycle` | cap на число источников за цикл (60). Обход идёт в порядке приоритета, поэтому бюджет уходит на те, кто реально даёт; 60 держит цикл внутри одного интервала |
цикл (0 = все).

### `regexp.txt` — как выдирать

Это настройки для `Extractor` (см. `proxy/extract.go`): что делать с
полученным HTML, чтобы достать `ip:port`.

Схема работы (важно, чтобы ты не дублировал руками):

1. **«Универсальные» паттерны применяются всегда, их в файл писать не надо:**
   * `scheme://ip:port` (`http://1.2.3.4:8080` — протокол сохраняется);
   * `голый ip:port` (`1.2.3.4:8080` — протокол неизвестен, будет
     угадан из `[checker].probe_order`: http → socks5 → socks4 → https);
   * `[ipv6]:port`;
   * **spys.one-обфускация портов** — места, где порт спрятан в
     `document.write("..."+(a^b)+(c^d)...)`. Не нужен браузер: `Extractor`
     сам находит переменные в других `<script>`-блоках страницы и считает
     XOR. Это магия, но магия рабочая.
2. **В `regexp.txt` кладём только то, что универсальные не поймали:**
   сайт-специфичные форматы, где ip и порт **не соседние** — таблицы с
   ячейками, `<a href="/ip/port">`, JSON, `data-ip`/`data-port` аттрибуты
   и прочие извращения верстальщиков.

Правила написания правил:

* **Одна регэксп-строка на строку файла.** Пустые строки и `#`-комментарии
  пропускаются. Плохая регэкспа падает при старте: `bad regex "..."`.
* **Нужно ровно 1–2 capture-группы**, причём:
  * 2 группы = IP + порт в любом порядке (порядок групп автодетект:
    «что похоже на IP — тот хост, другое — порт»);
  * 1 группа = только IP, а порт-число лежит **до** него в тексте
    (паттерн вроде `port-8080 ... 1.2.3.4`). Пример уже в файле.
* **Регэкспы намеренно ленивые**: ритмичные `[0-9]{1,3}`… валидация IP и
  порта (октеты ≤ 255, порт ≤ 65535) происходит в коде. Не пытайся впихнуть
  весь интернет в одну регэкспу — у тебя будет всё равно меньше парность,
  чем у `validHost`.
* **IPv6**: табличный `[ipv6]:port` уже покрыт универсальным паттерном;
  для экзотики в таблицах есть готовый пример с `[0-9a-fA-F:]{2,45}`
  (в файле, `IPv6 in tables`).
* **Порт в отдельном `<span>`/`<b>`** — тоже зафиксировано в файле.
* **Совет**: если сайт использует `class="proxy"` или `id="proxylisttable"`,
  смотри на аналогичные паттерны в `regexp.txt` — `free-proxy-list.net`,
  `hide.mn`, `proxynova` там уже разобраны. 90% таблиц интернета — клоны
  одних и тех же шаблонов.

Что делать, если сайт есть в `sites.txt`, но `collector.log` пишет
`-> 0 candidates`:

1. Открой страницу — может, капча, тогда это не про регэкспы.
2. `Ctrl+U` (исходник) и `Ctrl+F` по `port`. Так ты увидишь, в каком
   формате реально живут данные.
3. Если рядом с URL в списке есть протоколь-подсказка (`http.txt`) —
   она должна точно совпадать с форматом внутри. Иногда файл
   переименован, а внутри — совсем другой формат.

**Насмотренность протокола**: отдельный механизм `schemaNear` — для
per-site паттернов код смотрит на ±80 символов вокруг находки в поисках
слов `http`/`https`/`socks4`/`socks5` и проставляет схему даже из
«табличных» списков. Так что не мучайся: регэксп, который просто находит
`ip:port` в таблице, может сам получить подсказку про протокол из
соседнего текста.

### `document.write`-списки (Proxynova, GeoNode)

Часть сайтов не отдаёт список в HTML, а собирает его в браузере через
`document.write`. Для них в коде есть отдельный разбор (`proxy/jswrite.go`):
понимает склейку строк, `concat`, `repeat`, `split().reverse().join()`,
`atob`, вложенные `document.write` и `String.fromCharCode` со сдвигом. На
Proxynova снимается 35/35 строк, на GeoNode — 25/25 записей (регрессии лежат
в `proxy/testdata/`, проверяются `go test ./proxy/ -run Extract`).

Если новый сайт из этой породы не разбирается: сначала посмотри, что именно
пишет страница (`Ctrl+U`, вкладка Sources/Network), и не пиши паттерн в
`regexp.txt` под HTML, которого в ответе нет. Разбор живёт в коде, а
`regexp.txt` — только для обычных текстовых/табличных форматов.

## 4.6 Админка: три вкладки на одном порту

`http://127.0.0.1:9090/` (или то же самое по `https://` — порт отвечает на
оба протокола). Страница обновляется сама раз в 15 секунд.

**Live proxies** — что реально работает. Четыре определения, и разница между
ними существенна:

| scope | что значит |
|-------|------------|
| `hot` (по умолчанию) | кураторский хвост, из которого пикер берёт прокси — «работает прямо сейчас» |
| `served` | строгое подмножество: через прокси реально ушёл клиентский запрос за окно |
| `checked` | плюс те, кто прошёл полную проверку, но ещё не работал |
| `all` | вся очередь, включая непроверенных. Это диагностика, а не список для использования |

Окно — 15 минут. Кнопка **Download .txt** отдаёт выбранный scope построчно
(`socks5://1.2.3.4:1080`), без заголовков JSON. Если в ответе JSON пришло
`count` меньше `total` — это страница выдачи, а не весь список; текстовая
выгрузка при этом не ограничена.

**Sources** — телеметрия по каждому URL из `sites.txt`: `alive`, `yield_pct`
(доля выданного, ещё живая), `emitted`, `found`, `cycles`, `fails`, состояние
(`not fetched yet` / `ok` / `failing` / `cooling`). Источники, которые коллектор
ещё не обходил, помечены `unproven` — их отсутствие в таблице «плохих» ничего
не значит, они просто ещё не проверены.

**sites.txt** — редактор списка источников прямо в браузере: добавить строку,
удалить. Пишется атомарно (временный файл + rename), предыдущее содержимое
остаётся в `sites.txt.bak`, комментарии и порядок строк сохраняются, пустым
список сделать нельзя. Рестарт не нужен: коллектор перечитывает файл в начале
следующего цикла (до 25 минут ожидания). То же самое умеет
`POST/DELETE /api/sites` с `{"url": "..."}`.

Все ответы API — JSON, включая ошибки: `{"ok": false, "error": "...", "code": 400}`.

## 5. Аварийные сценарии

### 5.1 «Очередь пустая, бот не ходит»

Смотри:

```powershell
Invoke-RestMethod http://127.0.0.1:9090/health
```

`queue_live: 0` → ты на мели. Встроенный сторож после **2 пустых минут**
напишет в `system.log`:

```
queue: CRITICAL empty for 2+ minutes - proxy is unusable; waking collector
```

…и принудительно разбудит коллектор, не дожидаясь 25-минутного `cycle_sleep`.

Что делать:
- Глянь `collector.log` — если сайты отдают `captcha`, `403`, `521` или висят — это внешние капризы интернета, а не твой код.
- Проверь, что `sites.txt` не пуст и сайты живы.
- Если очередь была бы завалена добром, а тут вдруг ноль — подозревай, что
  вся твоя «живая» толпа на деле одна и та же (одна сетка прокси, все умерли вместе).

### 5.2 «Порт занят»

`http: proxy listening on ... : bind: address already in use` — вторая копия
уже работает. `stop.ps1`, потом `start.ps1`. Или пусть умирает: `stop.ps1` сам.

### 5.3 «Капчи повсюду / зарубежные сайты не открываются»

Ротация = лотерея: часть прокси умирает, часть «капчит». Это не баг
программы, это расплата за «свежесть». Проверь, насколько хорош твой
пул: `queue_hot` в `/health` — это прокси, подтверждённые недавней работой.

### 5.4 «Прокси выжил, но ничего не вставляет»

`prepare_tunnel`/`serve_connect_probe`: после «200 Connection established»
проект ждёт первый байт от цели, и если прокси притворяется живым, но молчит —
он получает заслуженный «serving failure» и заменяется. Это фича.

### 5.5 «Хочу прям сейчас увидеть рабочий прокси - гуляю»

`debug_proxies.txt` — до 50 URL свежих принятых прокси. Вынь строку оттуда,
суй в браузер. Если через неё всё работает, а через систему — нет, значит
проблема в нашей логике, а не в пуле. Самый ценный файл для дебага.

| Действие | Последствие |

| удалить строку из `regexp.txt` «на короткое время» | коллектор молча недобирает формат, которому она помогала, а ты потом гадаешь, почему сайт даёт 0 |
| дописать в `regexp.txt` паттерн без capture-групп | регэкспу нечего вернуть — `Extractor` проигнорирует находку (нужно 1–2 группы) |
| открыть `9090` в интернет | см. п.1 |
| убрать `noiseWriter`/поставить свежий `log.New` в листенеры | потоп `TLS handshake error` в system.log каждый день |
| поставить `serve_retries = 0` | попытки «поберечь попытки» = застрявшие запросы |
| написать свой `checkLoop` с неблокирующим `emit` | потеря кандидатов «чтобы быстрее» — а это минус к полноте пула. emit блокирующий, и это правильно |
| снова запустить второй инстанс | «bind: address already in use» + загадочное поведение |

## 7. FAQ (коротко, как умею)

**Q: Зачем сутки собирать 55k прокси, если работают 6?**
A: Ротация живёт на потоке. Очередь — это резервуар на проточке: ревалидация
каждые 15 минут отсеивает мёртвых, коллектор подливает свежих. 6 живых из
55k — это «нормальная осень».

**Q: Что значит здесь `sticky`?**
A: Прокси «прилипает» к TCP-соединению клиента на `serve_pin_ttl` (10 минут) —
не пережёвываем роллы на каждой картинке страницы. Можно дополнительно
пинить через заголовок `X-Sticky-Session` (строка-ключ), он срезается перед
форвардом. Прилипший прокси сдох — автоматически перебирается на свежий.

**Q: Я вижу в логе `Via` у себя в заголовках — это плохо?**
A: Нет. Это «протокольный след» прокси. Плохо, когда в `Via`/`X-Forwarded-For`
протекает *твой* IP — на это есть `leak_probe_urls`, такие прокси отбрасываются.

**Q: Сколько логов можно накопить?**
A: `logs/*.log*` — до 5 поколений по 32MB на каждую категорию. Это ~640MB
в худшем случае. Само очистится.

**Q: А если всё сломалось совсем?**
A. Порядок:
1. `-Check` — проверь конфиг.
2. `stop.ps1`, потом `start.ps1`.
3. `instance_err.log` и `logs/system.log` — там правда (или её отсутствие).
4. Если и это не помогло — загляни в `sites.txt`: возможно, интернет
   изменил адреса, а мы всё ещё стучимся в прошлое.

**Q: Зачем вся эта «проверка на стабильность выхода»?**
A. `require_stable_exit` режет прокси, у которых IP прыгает между пробами:
это либо ротаторы-воры, либо сетки, где «один адрес у всех». Для приватности
«один на всех» = «всё видно всем».
